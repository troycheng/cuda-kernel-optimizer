# V1.5 设计规格：主张与证据适用性

状态：实现依据

V1.5 不改变 V1.4 的权责划分。ChatGPT 仍是唯一优化决策者；工具仍只执行一次明确操作并保存事实。本版本修正的是 V1.4 遗留的阶段式证据模型：工具不能因为依次运行了 correctness、benchmark 和 paired A/B，就默认这些观测足以支持当前结论。

## 1. 核心模型

GPU 优化要验证的是一个受约束的因果主张：在冻结的 workload 和运行环境中，预定实现变化在保持必要语义的前提下造成了可测量的性能变化。

一份观测只有同时满足以下条件，才能成为支持该主张的证据：

1. 被测对象的有效身份明确；
2. reference 与 candidate 之间允许改变的内容明确；
3. 当前比较要求保持的语义和诊断信息明确；
4. 测量生命周期、共享状态和重建状态明确；
5. 影响判断的外部事实有匹配版本的来源，或明确保持为未解决假设。

一次 driver 调用可以产生多种证据。执行器按当前主张所需证据生成最小调用计划，不再为 correctness 和 measurement 机械重复完整 workload。

## 2. 现有模型中的唯一归属

| 内容 | 唯一归属 |
|---|---|
| 用户最终性能目标和业务精度要求 | Target |
| reference 与 candidate 的关系、额外语义检查、测量设计、实质性外部前提 | Experiment |
| 本次 operation 的确定性 driver 调用计划 | Invocation request |
| 实际运行身份、测量条件、正确性与性能观测 | driver evidence bundle 和 Invocation result |
| 证据是否充分、是否继续以及是否采用候选 | ChatGPT |

不新增 Comparison、Plan、Decision、Controller 或其它顶层持久对象。`workload_evaluate.py` 仍是唯一 workload 执行入口。

## 3. Experiment 的比较契约

Experiment 增加一份内嵌 `comparison_contract`，冻结：

- 双方关系：等价实现、不同 artifact 的质量比较，或部署效果比较；
- Target 业务精度门禁之外，本次关系要求的附加 gate；
- 只用于解释结果、不能拒绝候选的 diagnostic 指标；
- `same_process` 或 `isolated_process` 测量生命周期；
- 哪些状态必须共享，哪些状态会重建，以及选择该设计的理由。

Target 的 correctness 始终表示用户真正需要的结果质量。Experiment 的附加 gate 只表示本次实现关系要求保持的不变量，不能反向升级为其它 Target 的业务质量要求。同一指标不能同时是 gate 和 diagnostic。

Experiment 还可以记录少量 `material_premises`。每项只包含：技术主张、组件和版本、当前证据状态、来源以及它影响的决定。它不是研究日志，也不触发自动检索。状态中的 `primary_source_claim` 只表示主张来自一手资料，不能表示工具已认证其真实性；未解决前提使用 `unresolved_hypothesis`，可以用于设计判别实验，但不能伪装成已确认事实。

## 4. Driver evidence bundle

公开 driver 协议升级为单一 V2，不保留 V1 兼容分支。

每次请求包含一个或两个 subject：

- 单 subject 表示 baseline、隔离运行或 profiler 包装；
- 双 subject 表示同进程成对比较。

driver 每次返回完整 evidence bundle：

- 每个 subject 的 correctness metrics；
- 每个 subject 的 primary 和 constraint samples；
- 实际 acquisition context；
- 实际 runtime provenance；
- 原始 artifacts 和 cleanup 结果。

`same_process` 只保证两个 subject 进入同一次 driver 调用并接收同一个共享对象。通用协议无法
检查 workload 内部另行管理的服务、远端进程或外部缓存；依赖这些状态的主张必须由 driver
额外保存实际身份。请求中的 acquisition 回显本身不能证明这些外部状态确实共享。

driver 声明以下能力：

- 必需的 `single_variant_combined`；
- 可选的 `paired_same_process_combined`。

工具不会自动决定是否需要同进程比较。ChatGPT 在 Experiment 中选择；执行器只验证 driver 能力满足已经冻结的比较契约。

## 5. 有效运行时身份

runtime provenance 至少包含：

- 本次实际运行环境的不可变身份；
- host 或 container 类型；
- container lineage 是否完整；host 身份必须完整且不包含 image lineage；
- 已确认的 base 和 overlay 身份；
- 会影响被测路径的运行时组件及其 hash、commit 或其它不可变身份。

来源不完整不会使当前 workload 的原始观测消失，但会收窄它能够支持的归因范围。只冻结了最终 runtime identity 时，结论只能归属于该 runtime；不能据此声称结果来自未修改的 upstream 组件。

## 6. 最小证据调用计划

Invocation request 在 worker 启动前冻结完整 `evidence_plan`。每个步骤明确 subject、case、pair、顺序和 acquisition context；worker 只能按该计划执行。final audit 还预先冻结每个 case 的 original-only 条件恢复检查，只有主比较出现 candidate gate 失败且仍缺 original 正确性时才启用。

设 case 数为 `C`、pair 数为 `P`：

- baseline：`C` 次调用；
- 隔离进程比较：`2 × P × C` 次调用；
- 同进程成对比较：`P × C` 次调用。

combined evidence 中的 correctness 和 measurements 同时进入结果。第一次出现的合格 correctness 可满足对应 subject/case 的正确性要求；不再额外执行 `2 × C` 次 correctness workload。任一 gate 失败后停止尚未启动的性能步骤。final audit 若要判断是否能够恢复 original，只运行已冻结的 original-only 条件检查以补齐缺失 case，不再启动 candidate 或剩余性能配对。

该计划只服务当前 operation，不记录下一步、不跨 Invocation 恢复，也不判断 ROI，因此不是优化 Controller。

## 7. 结论适用性

结果必须保留：

- 当前 comparison contract 的摘要；
- 实际 evidence plan 和完成情况；
- 每项 gate 的计算结果；
- diagnostic 原始值；
- acquisition context；
- runtime attribution scope；
- 被跳过的剩余调用和停止原因。

环境身份、比较关系或测量条件不匹配时，工具拒绝相应性能归因；正确性等其它独立证据仍按实际适用范围保留。

## 8. 实现边界

- 不增加生产模块或公开 operation；
- 不增加自动研究、自动方向选择或自动 ROI；
- 不按容器、route、PDL 或某个模型编写特判；
- 不同时维护 V1/V2 driver 协议；
- 删除以 `correctness`、`measure`、`combined` 为阶段推进依据的重复 worker 分支；
- 只在 `readiness.py`、`workload_adapter.py`、`workload_evaluate.py` 及直接消费公开结果的现有模块中修改实现。

## 9. 验收

验收围绕模型不变量，不按历史问题堆测试：

1. 一次 evidence bundle 能同时满足正确性和性能要求，正式比较不重复启动；
2. runtime provenance 不完整时，结果保留但归因范围收窄；
3. 相同 correctness metric 可以在一个 Experiment 中作为 gate，在另一个 Experiment 中作为 diagnostic；
4. 同进程比较必须返回两个 subject，并绑定共享和重建状态；隔离比较不得伪装成同进程证据；
5. material premise 未核实时保持为假设，不作为已确认外部事实；
6. 现有 Champion、CAS、timeout、process-group cleanup 和 immutable artifact 约束保持成立。

历史 MXFP6/PDL 材料只用于回放这些不变量，不进入通用生产逻辑。

## 15. 外部技术前提的知识支撑

本项目携带知识的目的不是替 ChatGPT 决定优化方向，也不是离线保存尽可能多的 GPU 资料。它只用于降低一种高代价错误：ChatGPT 根据未经核实或版本不匹配的外部技术前提，误判候选是否可行、安全或值得继续。

一次优化判断中的不确定性分为三类：

| 不确定性 | 主要解决方式 |
|---|---|
| 当前 workload 的瓶颈在哪里 | baseline、profile、源码和运行观测 |
| 候选在当前 workload 上有多少收益 | 最低成本实验和正式目标比较 |
| 某项外部机制在当前版本中保证什么 | 一手技术资料、版本绑定的本地材料，必要时源码核验 |

本地知识只重点支撑第三类。第一类和第二类仍必须来自当前 Target，不能用知识卡替代。

### 15.1 三类材料

同一知识索引可以保存三类材料，但三者不能具有相同的证明力：

- **技术契约**：一手资料明确规定的语义、适用条件、版本边界和不保证事项；可以用于核实外部技术前提。
- **优化经验**：根据常见现象提出候选或最低成本观测；只能帮助生成方向，不能证明机制适用或收益成立。
- **实践案例**：某个冻结环境中的成功、失败或反例；只证明该环境中的事实，跨环境使用时仍是参考材料。

技术契约应是原子命题，而不是整章手册的摘要。每项至少回答：规定了什么、适用于什么身份、来源的准确章节、没有规定什么、错误理解会影响哪个决定。最低成本实验由 ChatGPT 根据当前 Target 设计，不固化为静态技术事实。

### 15.2 查询器的职责边界

`knowledge_query.py` 仍只执行一次有界查询，不新增 Resolver、Planner 或其它顶层对象。它只返回：

- 材料的种类和内容；
- 材料绑定的组件、版本、架构及其它适用条件；
- 当前 Target 身份与材料所声明的条件是兼容、相关但不充分，还是不匹配，并给出字段级原因；该关系只描述材料匹配，不能推导机制是否受支持；
- 一手来源的 URL、章节定位、版本和核验时间；
- 技术契约明确没有支持的推论。

查询器不输出“前提已解决”“机制受支持”“应该继续”等决定。空结果只表示本地索引没有返回材料；身份不兼容的材料也不能静默消失，否则 ChatGPT 无法区分“已知不适用”和“尚未收录”。是否需要联网核验、源码检查或判别实验，以及材料是否足以解决 `material_premise`，仍由 ChatGPT 判断并记录到 Experiment。

### 15.3 决策不对称性

未核实的机制可以作为候选来源，但不能单独支持以下高代价结论：

- 删除同步、精度或安全相关代码；
- 认定某个高价值机制在当前平台不可用；
- 关闭整个机制，而不只是拒绝当前实现；
- 形成 Target 的 terminal reason。

这些结论必须有适用于当前身份的技术契约、源码证据或能够区分该机制的本地实验。知识缺失不阻止 ChatGPT 继续从源码、profile 和实验提出方向，也不构成反对某个方向的证据。

## 16. 跨技术栈决策回放

回放使用实现前的 `knowledge_query.py`、106 张知识卡和 21 个来源，不修改生产代码或知识内容。外部事实只使用一手资料。目标不是证明材料覆盖全面，而是尝试找出第 15 节模型无法处理的场景。

| 场景 | 当前实现的表现 | 正确处理 | 对核心模型的结论 |
|---|---|---|---|
| CUDA PDL，SM90 | 命中一张 `source_verified` 方法卡，但问题文本为 `Does None...`，没有返回同步与可见性语义，也没有来源章节 | 返回 PDL 的版本化技术契约；ChatGPT 判断 secondary 的同步点、独立工作和资源条件 | 技术契约与优化经验必须分开；“来源已核验”不等于命题已核实 |
| CUDA PDL，SM120 | 与完全未知机制一样返回空结果；现有卡还错误地把架构限制在 SM90/100/103/110，而官方契约是 compute capability 9.0 及以上 | 返回相关 PDL 材料及“卡片声明与 Target 不匹配”的具体字段；ChatGPT 对照一手资料后应判定本地材料过期或错误，不能判定 SM120 不支持 | 身份过滤会同时掩盖“材料不适用”和“材料本身错误”；空结果没有否定含义 |
| CUTLASS Blackwell | 当前方法卡把多个 Blackwell 架构并列，不能表达 SM100 与 SM120 指令和 binary 兼容边界 | 以具体 CUTLASS/CUDA 版本和目标架构核实能力；构建与运行结果仍只证明当前 artifact | 架构名称相近不能替代版本化契约，真实实验保留环境边界 |
| Nsight Systems 空闲区间 | 能返回 launch-gap 经验，但来源 URL、章节和 profiler 口径未投影给调用方 | 先把 time utilization、资源利用率和 profiler overhead 区分开，再决定是否追查 CPU launch | profiler 语义属于技术契约；瓶颈归因属于当前 workload 观测 |
| PyTorch graph break / vLLM fallback | 能返回宽泛的 workload 方法，但没有暴露框架版本适用性和 fallback 的实际运行身份 | 用当前框架版本的契约解释 graph break/fallback，再从 runtime provenance 确认实际路径 | 文档语义和本机执行路径必须同时成立，任何一方都不能单独证明收益 |
| NCCL collective 等待 | 能返回 rank-skew 诊断经验，但查询的 NCCL 2.27.3 会关联 2.30.x 来源，且未返回版本差异 | 区分各 rank 的 collective 参数契约、异步 stream 完成语义和实际到达偏斜 | 通信契约、系统观测和优化方向是三个不同证据层次 |
| 尚未收录的新机制 | 返回空结果 | ChatGPT 继续检查源码、profile、在线一手资料或设计判别实验 | 知识库不是候选准入表，也不能成为优化能力上限 |

一手资料核验：

- [CUDA Programming Guide 的 PDL 章节](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html)规定该能力从 compute capability 9.0 开始可用；secondary 可能在 primary 完成和全局内存刷新前启动，依赖数据前必须执行 `cudaGridDependencySynchronize()` 或等价同步；并发只是机会，不是保证。
- [CUTLASS Overview](https://docs.nvidia.com/cutlass/latest/overview.html)明确区分数据中心 Blackwell SM100 与 GeForce Blackwell SM120，架构条件特性编译出的 binary 不能跨两者直接等同使用。
- [Nsight Systems Analysis Guide](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html)明确其 GPU utilization 是时间占用而非资源占用，且包含部分 profiler overhead。
- [PyTorch profiling 文档](https://docs.pytorch.org/docs/stable/user_guide/torch_compiler/torch.compiler_profiling_torch_compile.html)把 graph break 描述为编译区域中断；[vLLM 调试文档](https://docs.vllm.ai/en/stable/design/debug_vllm_compile/)说明 `--enforce-eager` 会同时关闭 `torch.compile` 集成和 CUDA Graph。
- [NCCL 2.30 collective 文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)规定各 rank 必须以相同 count 和 datatype 参与；[异步状态文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/nccl4py/communicator/status.html)区分 CPU 侧入队成功与 CUDA stream 上实际完成。

回放没有要求修改第 15 节的权责边界，但否定了让查询器自行给出“已解决/未知”等决策状态的设想。查询器只能报告材料及适用关系；ChatGPT 才能结合当前源码和实验证据解决前提。

## 17. 最小实现范围

在上述回放通过后，知识侧生产实现只允许落在现有 `cards.json`、`sources.json`、`knowledge_query.py` 和直接测试中；用户文档与 skill 说明只同步实际行为，不增加另一套规则：

1. 先将现有内容按技术契约、优化经验和实践案例重新审计；删除占位字段、重复卡和无法改变决策的内容，不在迁移前扩充卡片数量。
2. 查询结果补回当前已被 projection 丢弃的适用条件、来源 URL/章节、技术命题和不支持的推论。
3. 身份不匹配时返回相关材料和具体差异，不再与“没有收录”产生同样的空结果。
4. 只先保留少量错误代价高、跨 workload 复用率高的技术契约：同步与内存可见性、硬件/版本支持边界、编译提示的保证范围、profiler 指标语义、框架 dispatch/fallback 和通信顺序。
5. 用本节六类回放作为行为验收；不为每张知识卡堆独立测试，也不下载整本手册进入仓库或默认上下文。

如果实现需要新增生产模块、自动方向选择、知识准入流程或第二套决策状态机，应停止并重新审查，而不是继续扩张。
