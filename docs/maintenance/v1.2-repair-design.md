# V1.2 自适应投入控制修复计划

> **面向 AI 代理的工作者：** 按本文顺序执行。共享 Controller 状态的任务必须由同一
> 个实现者连续完成；不要并行修改 `workload_controller.py`。每项先写失败测试，再做
> 最小实现，最后提交。

**目标：** 在保留 V1.2 诊断能力的前提下，把执行控制收敛为“一次运行级授权、阶段级
投入判断、只在计划实质变化时追加询问”，并删除现有重复和断裂的控制协议。

**架构：** readiness、原始 workload baseline 和首次全局 profile 组成固定 bootstrap。
bootstrap 完成后生成初始投入建议；后续 evidence 和候选验证由一份运行级授权约束。
Controller 每次只提交一个候选阶段，阶段完成后根据新证据和实际耗时决定下一步。

**技术栈：** Python 3 标准库、`unittest`、现有 content-addressed Controller state、
现有 workload/evidence adapters。

**代码基线：** V1.2 实现快照为 `0af8054`；冻结本计划后的修复起点为 `21491bd`。

## 1. 冻结的设计结论

### 1.1 三种时间不能混用

| 时间 | 用途 | 是否用于授权扣减 |
|---|---|---|
| 命令安全超时 | 防止 build、profile、benchmark 或 reviewer 卡死；超时终止进程组 | 否 |
| 受控执行耗时 | 已完成 evidence、reviewer 和候选阶段的实际耗时 | 是 |
| 墙上时间 | 向用户说明整个任务经历了多久，包括等待和离线 | 否 |

readiness、baseline 和首次全局 profile 的实际耗时记录为
`bootstrap_execution_seconds`。它们由启动请求隐含授权，不从后续授权中重复扣减。

后续授权只扣减 Controller 能证明已经执行的动作。用户等待、暂停、离线时间和模型
思考时间不得伪装成 `controlled_spend_seconds`。模型 token 使用如果运行环境没有提供
可信计数，就显示为 `unknown`，不由 Controller 猜测。

### 1.2 一次运行级授权

正常交互在初始投入建议后合并一次授权。无人值守模式由用户的初始请求形成授权，不在
运行中计划性询问。只有预计投入、mutation scope、风险或最高验证阶段超出原授权时，
才返回 `REVIEW_REQUIRED`。

授权输入只包含以下字段：

```json
{
  "schema_version": "cuda-workload-optimizer/authorization-v1",
  "grant_id": "stable-id",
  "source": "initial_request",
  "interaction_mode": "unattended",
  "max_controlled_seconds": 3600,
  "allowed_mutation_scopes": ["project"],
  "max_risk": "medium",
  "max_stage": "formal_paired"
}
```

`source` 只接受 `initial_request` 或 `interactive_confirmation`；
`interaction_mode` 只接受 `interactive` 或 `unattended`。Controller 在封存时补充
control、workload、baseline、environment 和 active-diagnosis epoch identity。每份
grant 写入 `active_diagnosis/authorization_grants/<grant_id>.json`，通过
`previous_grant_sha256` 形成追加链，当前 digest 写入 content-addressed state。授权不
按墙上时间过期；identity 变化才使它失效。

这份记录只是可审计的执行边界，不声称能在没有宿主产品签名的情况下密码学证明用户
同意。Controller 负责验证“执行没有超出输入边界”。

### 1.3 ChangeSet 是唯一候选计划

ChangeSet 保存：

- 实际 mutation scope 和 risk；
- claim layer；
- 最便宜证伪阶段；
- 当前 claim 实际会执行的阶段 P90 上界及其来源；
- minimum effect；
- rejection condition；
- promotion condition。

运行级授权保存时间、scope、risk 和最高阶段。两者不得复制彼此的事实。
`candidate_proposal`、proposal archive、freshness 和 proposal stale 生命周期全部删除。

`register_change()` 只验证一次调用输入，并将规范化后的 ChangeSet 封存在
`rounds/round-1/change_set.json`；state 的 `change_set_digest` 绑定这份冻结 artifact。
它是登记完成后的唯一候选计划。根目录 `change_set.json` 仅是输入兼容镜像，不再被
stage、resume、reviewer 或 promotion 读取，reviewer 也不得重写它。冻结 artifact 与
state digest 不匹配时 fail closed；兼容镜像漂移不得改变已登记候选。

每个阶段的成本记录为：

```json
{
  "p90_seconds": 30,
  "basis": "declared_upper_bound"
}
```

V1.2 的 candidate stage `basis` 只接受 `declared_upper_bound`。当前实现没有一份
Controller 封存、按 candidate stage 和 identity 生成的 P90 来源；仅增加
`current_run_measurement` 或 `identity_matched_history` 标签无法证明数值来源。
这两类来源留到 V1.3 建立 timing calibration artifact 后再开放。P50 不由 ChangeSet
填写；没有可验证的 identity-matched history 时，investment brief 必须给出 `null`。

当前 workload Controller 只接受 `workload` claim，其可执行阶段为：

```text
static_review
build_correctness
short_paired
profiler          # 仅当存在明确且可由 profiler 回答的不确定性
formal_paired
```

workload candidate 不再填写 `service` 成本。serving claim 继续由独立 serving workflow
处理，不在 V1.2 中新增 service adapter。

### 1.4 阶段级判断，不是阶段级授权

Controller 在每个候选阶段前调用纯决策器。决策器只返回：

```text
RUN_STAGE
STOP
PROMOTE
REVIEW_REQUIRED
```

判定条件必须可审计：

1. 收益上限低于 project minimum effect：`STOP`。
2. 前置阶段失败：`STOP`，后续昂贵阶段全部跳过。
3. 下一动作不能改变当前决定：`STOP` 或跳过该动作。
4. 仍有必要时，选择剩余阶段中成本最低的证伪动作。
5. 下一阶段 P90、scope、risk 和阶段等级都在运行级授权内：`RUN_STAGE`。
6. 路径仍可能有价值但超出授权：`REVIEW_REQUIRED`。
7. 正式成对证据的下界达到门槛且约束通过：`PROMOTE`。

一个候选被证伪后，Controller 在同一授权内自动回到仍未关闭、未重复且收益上限达标
的下一方向；这不产生计划内询问。只有所有合格方向都关闭或收益上限低于门槛时，才
返回 `STOP`。

不增加“成功概率”或黑盒 ROI 分数。V1.3 可以改善 benefit ceiling、证据置信度和成本
预测，但不改变上述 Controller 接口。

### 1.5 使用现有 state 做阶段恢复

不新增 `candidate_session.json` 或模板 schema。state 保存：

```text
authorization_grant_sha256
controlled_spend_seconds
candidate_stage
candidate_stage_intent_sha256
candidate_stage_completions{stage: complete}
candidate_after_identity_digest
review_call_intent_sha256
review_call_completions{review_id: complete_sha256}
```

每个阶段复用两个内部 marker：

```text
candidate_stage_intent.json
candidate_stage_complete.json
```

执行顺序：

1. 写 intent，并提交绑定 intent digest 的 state；
2. 在独立进程组运行一个阶段；
3. 原子写入阶段 artifact；
4. 写 complete marker，绑定 intent、候选、ChangeSet、stage artifact digest 和实际耗时；
5. 提交新 state，把完整 complete 写入 `candidate_stage_completions[stage]`，清除
   intent state binding；digest 和 Gate result 都从该对象按需派生；
6. 清除 marker；
7. 重新计算下一阶段。

有 complete、state 未推进时，`resume` 只提交结果，不重跑。只有 intent、没有 complete
且 state 已绑定 intent 时进入 `manual_recovery_required`，不得猜测命令是否完成，也
不得自动重复昂贵阶段。state 已提交 complete、marker 尚未清理时只做清理，不重复扣减。
intent 尚未绑定 state 时 runner 一定没有启动，可以安全丢弃并重新裁决。

### 1.6 暂停与放弃

`REVIEW_REQUIRED` 不是性能失败。暂停时保留当前 candidate，绑定
`candidate_after_identity_digest`，不执行“回滚后再恢复候选”的快照往返。

- 新授权仍覆盖当前 candidate：`resume` 从 `candidate_stage` 继续；
- 用户放弃：`abandon` 恢复原 snapshot；
- candidate 或 workspace identity 漂移：进入 manual recovery；
- 正确性、性能或约束失败：回滚并回到 active diagnosis 的下一方向。

这样正常过程不因每个阶段询问用户，异常暂停也不需要第二份 candidate snapshot。

### 1.7 初始投入建议

首次全局 profile 和 performance model 生成后，立即写
`active_diagnosis/initial_investment_brief.json`。它包含：

- 当前主要瓶颈和可移除时间上限；
- minimum effect；
- 最大不确定性；
- bootstrap 实际耗时；
- 下一步为 `propose_hypotheses`；
- 尚无身份匹配数据的 P50/P90 明确写 `null`，basis 为 `unavailable`。

它不是候选 promotion 决策，也不触发代码修改。后续有具体 action 后继续使用现有
`investment_brief.json`。

### 1.8 外部审查与分支探索

外部 reviewer 继续只在方向选择、明显平台期和最终审查触发，并行总等待不超过
180 秒。外发请求必须由 allowlist summary 构造，不包含原始路径、主机名、环境变量、
业务输入、完整日志或默认 diff。外部结果只作挑战。

方向 reviewer 和最终 reviewer 使用同一套固定、不可配置的外呼提交协议，但各自保存在
自己的目录：方向审查使用 `active_diagnosis/direction_review/{intent,complete}.json`，
最终审查使用 `final_review/{intent,complete}.json`。外呼前写 request-bound intent 并
提交 state binding；返回后写 aggregate 和 complete；最后把 complete digest 与一次
`total_wait_seconds` 提交进 state，再清理 marker。complete 必须包含
`intent_sha256`、`request_sha256`、`aggregate_sha256`、`total_wait_seconds` 和
`completed_at_epoch`。匹配 complete 的恢复只提交，不重新外呼；state 已消费 complete
时只清理。只有 state-bound intent、没有 complete 的未知中断进入 manual recovery。
该协议不是通用事务 DSL，不能承载任意 writes/removals。

`branch_explore.py` 撤销 V1.2 对 `candidate_cost_bound` 的读取，恢复编排器能够识别的
`shortlist_ready` 和 `no_confirmed_kernel_win` 终态。V1.2 不为这条独立 kernel 分支
再复制一套 workload Controller 授权协议。

## 5. 模型与 token 使用方案

### 5.1 只建立三个执行上下文

| A | `gpt-5.6-terra high` | 任务 1、7 的机械部分 | 契约修复和文档范围明确，但仍提高一档推理，避免把错误测试继续固化。 |

### 5.3 token 约束

1. 先保证设计和实现闭合，再节省 token；不得用低强度模型反复试错替代一次高质量判断。
2. 主代理只负责任务边界、状态检查、提交范围和最终发布；不重复讲解实现。
3. 每个实现上下文只读一次冻结计划；文件只有在发生修改或验证需要时重读。
4. targeted tests 在每个 commit 前运行；完整 suite 只在任务 7 运行一次。
5. 测试失败先看首个真实失败，不把相同根因交给多个模型重复分析。
6. max/ultra 只处理编码前一致性、Controller state、授权、恢复协议和最终审查；纯契约
   修复、文档与测试数更新由 `gpt-5.6-terra high` 完成。
7. 外部 AI 只做一次最终挑战，不在普通候选或每个 commit 后调用。
8. 任何实现如果要求新增 schema、第二套 candidate snapshot 或第四种事务框架，立即
   停止并回到本计划检查范围，不让局部实现继续扩张。

### 6.2 一次性接口修正

本节是编码前最后一次规格收敛，后续实现不得再临时发明接口。

1. 新 run 的 state 增加 `investment_control_version: run-grant-v1`。完成态旧 run 只读；
   缺少该字段的未完成 run 在 `resume` 时不得启动命令，进入
   `manual_recovery`，原因为 `legacy_investment_control_requires_restart`。
2. `max_controlled_seconds` 是整条 run 的累计上限，不是本次 grant 新增的秒数。新 grant
   不清零 `controlled_spend_seconds`，且不得小于已经封存的 spend。
3. `max_stage` 的顺序固定为
   `diagnosis < static_review < build_correctness < short_paired < profiler <
   formal_paired`。`diagnosis` 允许诊断 evidence，但禁止登记 ChangeSet。
   `allowed_mutation_scopes` 可以为空，用于只分析、不修改的授权。
4. grant 的 `max_risk` 同时约束 evidence action 和候选；ChangeSet 顶层新增
   `risk`，它是候选提交者的权威声明。Controller 能校验和限制该声明，但不声称能从
   任意源码自动推断真实风险。
5. `candidate.estimated_cost[stage]` 使用 `{p90_seconds, basis}`。执行顺序由前置依赖
   决定，不强迫各阶段 P90 数值单调。V1.2 只接受
   `basis: declared_upper_bound`；没有可验证 source artifact 前不接受仅凭名称声明的
   measurement/history basis。
6. workload 必须声明 `static_review`、`build_correctness`、`short_paired` 和
   `formal_paired`；只有存在明确 profiler 问题时才要求 `profiler`，永远不要求
   `service`。
7. `CandidateGate` 只选择当前前置条件已经满足的下一阶段，不能为了数值更便宜跳过
   correctness 或 short screen。阶段开始前必须重新验证当前 candidate identity。
8. external reviewer 是可选挑战。如果剩余授权容不下其总等待上界则跳过并记录，不单独
   向用户申请授权；实际运行时只按并行聚合的 `total_wait_seconds` 扣减一次。
9. 每个受控命令的有效超时为命令安全超时和剩余授权中的较小值。Controller 已知的超时
   必须写出完成结果并返回 `REVIEW_REQUIRED`；只有进程或 Controller 意外中断、留下
   intent 而没有 complete 时才进入 manual recovery。
10. `abandon` 表示用户结束本 run：恢复原 snapshot，写
    `decision.status=abandoned`，state 进入 `completed/done`。V1.2 不再增加“跳过当前
    candidate 后继续探索”的第二种放弃语义。
11. 所有会启动 Controller runner 或写 run 状态的公开函数都必须先检查
    `investment_control_version`，不能只在 `resume` 检查。旧 run 只允许只读
    `status`，以及 snapshot 完整时的显式 `abandon`。
12. 方向和最终 reviewer 都必须在外呼前提交 intent；complete 绑定 request、aggregate
    和实际总等待。外呼完成后崩溃只能提交一次，state 已提交后崩溃只能清理 marker。

### 6.3 字段、读写和测试闭环

| 事实 | 唯一 writer | reader / admission | state transition | 必须锁定的测试 |
|---|---|---|---|---|
| 初始投入建议 | `_start_run_unlocked()` 调用 `build_initial_investment_brief()`，写 `active_diagnosis/initial_investment_brief.json` 和 state digest | `authorize_run()`、`status` | 固定 bootstrap 完成后仍为 `active/propose_hypotheses`，不得修改项目 | 无历史成本时 P50/P90 为 null；brief 篡改后授权失败 |
| 运行级 grant | `authorize_run()` / `authorize-run`；写 immutable grant、ledger event 和 `authorization_grant_sha256` | `_diagnostic_investment_inputs()`、evidence admission、`register_change()`、每个 candidate stage、`resume` | 首次授权不改变诊断方向；追加 grant 只更新边界；同 id 同内容幂等、异内容拒绝 | 非法 scope/risk/stage/数值；identity 漂移；artifact/ledger/state 三个中断点；缺失授权不执行 action |
| scope 与 risk | `register_change()` 验证 ChangeSet 顶层 `scope`、`risk`，写唯一冻结 artifact；state 绑定 digest | stage、resume、reviewer 和 decision 只读取冻结 artifact；根目录镜像不是 reader | `register_change -> edit_then_evaluate`；冻结 digest 漂移 fail closed；越界不创建 snapshot | 空 mutation scopes 可分析；scope/risk 越权不登记候选；根镜像漂移不改变候选；冻结 artifact 漂移不启动后续动作 |
| 阶段 P90 与 basis | ChangeSet 的 `candidate.estimated_cost`，V1.2 仅接受 `declared_upper_bound` | 纯 `CandidateGate.decide()` 和 Controller 的下一阶段 admission | 只允许当前 prerequisite 对应的一个 stage；授权不足保留 candidate | workload 无 service；profiler 条件必需；其它 basis 拒绝；P90 不必单调 |

| candidate markers | Controller 在 stage 前写 `candidate_stage_intent.json` 并将 digest 提交进 state；stage 后写 artifact 与绑定 intent 的 `candidate_stage_complete.json` | `evaluate`、`resume` | complete 未提交时只提交；state 的 completion map 已包含 digest 时只清理；state-bound intent 无 complete 才 manual recovery | static/correctness/short 失败不启动后续；complete 前后两个崩溃窗都不重跑或重复扣费；candidate 漂移不启动 stage |
| reviewer markers | 方向与最终 reviewer 各自在外呼前写 request-bound intent，返回后写 aggregate 和 complete | proposal publish、promotion、`resume` | complete 未提交时只提交一次 wait spend；state 已绑定时只清理；未知外呼中断 manual recovery | 两类 reviewer 分别覆盖 call 后/state 前和 state 后/cleanup 前中断；provider failure 仍形成 completion |
| pause / resume / abandon | gate 写 pause state；`authorize_run()` 链接新 grant；`abandon()` 写终态 | `resume` 校验 grant、ChangeSet、candidate identity 和 marker | pause 保留 candidate；覆盖后从 `candidate_stage` 继续；abandon 回滚并完成 | pause 不回滚；新 grant 精确续跑；不覆盖仍暂停；漂移 manual recovery；abandon 幂等 |
| terminal status | diagnosis、candidate gate、rollback、abandon 和 recovery 的专用完成函数 | 所有公开入口的版本 gate、`status`、`resume`，以及 branch 输出的 orchestrator reader | 见 6.4；不得用授权不足冒充性能 STOP | 每种 decision 到 state 的映射；旧 run 入口矩阵不启动 runner；branch 只返回 orchestrator 支持的终态 |

grant artifact 由用户字段加以下 Controller 绑定组成：

```text
control_digest
workload_source_hash
baseline_identity_digest
baseline_environment_identity_digest
analysis_epoch_sha256
previous_grant_sha256
sealed_at_epoch
```

`previous_grant_sha256` 首份为 `null`，后续必须等于 state 当前 grant digest。grant id 已
存在且内容完全相同时直接返回当前 state；同 id 不同内容拒绝。artifact 可以先落盘，
但 ledger 和 state 更新必须可从任一中断点幂等补齐，不能产生两条相同授权事件。

candidate completion 至少绑定：

```text
intent_sha256
authorization_grant_sha256
change_set_sha256
candidate_after_identity_digest
stage
stage_artifact_sha256
elapsed_seconds
completed_at_epoch
```

intent 本身绑定创建它的 `base_state_sha256`。state 用
`candidate_stage_intent_sha256` 表示 runner 可能已经启动，用
`candidate_stage_completions[stage]` 表示该 complete 已计入 spend。固定 marker
文件即使在 cleanup 前残留，也不能覆盖这两个 state 事实。

实际 stage 超过 P90 不是性能失败；已知命令超时按授权暂停处理。完成后若累计 spend
达到上限，不再启动下一阶段。

### 6.4 唯一状态映射

| 决定或事件 | state.status | state.next_action | candidate | 后续 |
|---|---|---|---|---|
| 初始 brief 完成、尚无 grant | `active` | `propose_hypotheses` | 无 | 等待授权或只返回分析 |
| `MEASURE` 且 action 获准 | `active` | `collect_evidence` | 无 | 执行一个 evidence action |
| `PURSUE` 且 ChangeSet 获准 | `active` | `edit_then_evaluate` | 登记并保存 snapshot | 修改后进入第一个 candidate stage |
| candidate stage `RUN_STAGE` | `active` | `evaluate` | 保留，推进 `candidate_stage` | 只执行一个阶段后重新判断 |
| `REVIEW_REQUIRED` | `active` | `review_required` | 原地保留 | 新 grant 覆盖后 resume；不回滚 |
| candidate `STOP` | `active` | `propose_hypotheses` | 回滚并记 failed identity | 自动选择其他合格方向 |
| diagnosis `STOP` | `completed` | `done` | 无 | 无合格方向或收益上限不足 |
| `PROMOTE` | `completed` | `done` | 保留修改 | 输出 promoted decision |
| 用户 `abandon` | `completed` | `done` | 回滚 | 输出 abandoned decision |
| identity 漂移或未知中断 | `manual_recovery_required` | `manual_recovery` | 不自动改变 | 只报告恢复说明 |

独立 kernel branch 不消费这套 run grant。任务 1 将它恢复为
`shortlist_ready` 或 `no_confirmed_kernel_win`；授权不足由外层编排器处理，不能再输出
第三种、reader 不认识的 `review_required`。

### 6.5 旧 run 与测试替换边界

- `status` 仍能读取 `completed/done` 的旧 run，不改写历史 artifact。
- 缺少 `investment_control_version` 的未完成 run 不自动迁移，因为旧 proposal 没有
  可验证的逐阶段 P90/basis，旧 gate 也没有 stage completion marker。
- 版本检查位于共享的内部 admission helper；所有公开 Python 入口和 CLI 都经过它，
  不能通过绕过 `resume` 继续旧协议。
- 旧 active candidate 如 snapshot 完整，可以显式 `abandon`；否则只报告 manual
  recovery 并要求新建 run。
- 删除 `seal-candidate-proposal` CLI；增加 `authorize-run` 和 `abandon`；保留
  `run`、`register-diagnosis`、`collect-evidence`、`register-change`、`evaluate`、
  `resume` 和 `status`。
- proposal freshness/archive、按 `deadline_epoch` 回滚、一次性 `CandidateGate.run()`
  以及 workload service 成本对应的测试必须重写，不能为了维持 340 项基线而保留双协议。

### 6.6 独立复核结论

独立复核没有发现 Critical，发现 4 个 Important，均已在本计划中闭合：

1. 删除没有可验证 source 的 measurement/history candidate cost basis，V1.2 只保留
   `declared_upper_bound`；
2. intent、complete 和 state completion digest 三方绑定，补齐 state commit 后、
   marker cleanup 前的恢复窗口；
3. 旧 run 的版本 gate 覆盖所有执行或写入入口，不只覆盖 `resume`；
4. 方向 reviewer 和最终 reviewer 都纳入 request-bound、只扣费一次的外呼提交协议。

批次 1～4 不得弱化上述四项来换取兼容旧测试；若实现需要再次改变这些接口，必须停在当前
批次重新审查，不能边编码边修改规格。

## 7. 最终验收

完成 V1.2 必须同时证明：

- 用户等待不扣减授权，墙上时间仍可见；
- 正常交互计划内最多一次授权，无人值守计划内零次询问；
- static、correctness 和 short screen 失败后没有启动后续昂贵阶段；
- 已完成阶段在 resume 后不重复；
- state 已消费 completion、marker 尚未清理时不重复执行或扣费；
- 缺失授权不会自动扩大为一天；
- workload candidate 不再携带无用 service 成本；
- V1.2 candidate cost 不接受无来源的 measurement/history basis；
- 有价值但超出授权返回 `REVIEW_REQUIRED`，无合格方向才返回 `STOP`；
- 所有 run-bound 写入和执行入口都会拒绝未完成的旧控制协议；
- branch explorer 的所有终态都能被 orchestrate 接受；
- 初始 profile 后立即有不编造成本的投入建议；
- candidate proposal 及其专用恢复代码已删除；
- reviewer 外发内容经过 allowlist；
- 方向与最终 reviewer 的匹配 completion 都不会重复外呼或重复扣费；
- 相对修复起点，生产代码净减少；
- targeted、完整本地 suite、self-check 和 diff check 全部通过。
