# 社区研究接入计划：提高诊断与实现选择的质量

日期：2026-09-06；执行更新：2026-09-07。状态：A/B 已实施，C 的本地定向检查完成；正式发布评测未运行，尚未提交或发布。结果见 [检查记录](diagnostic-knowledge-evaluation-2026-09-07.md)。
基线：本地 main `959c1ba`（V1.6.1）。本计划续接 8 月 31 日的社区研究，不恢复旧 Controller 或另建优化流程。

## 目标

让 ChatGPT 用更少的无关资料和无效实验，把性能现象解释清楚，找到适用的实现，并判断是否值得继续。首轮不扩充机制数量，不增加运行时操作、schema、依赖或自动调度。

保持现有分工：ChatGPT 判断原因、选择资料和实验；工具执行明确操作并保存事实。知识是帮助推理的材料，不是分类器、准入条件或自动处方。

## 现有实现与真实缺口

现有 `knowledge_query.py` 已能限制返回数量和字节数、输出适用范围、竞争解释、反证动作，并按需返回 playbook 路径。无需再写检索平台。`research_augmentation.md` 已涵盖上游复用与资料核验；`SKILL.md` 已有生产边界、ROI、最低成本实验和预测纠偏，不再重复追加这些规则。

当前有 97 张知识卡。抽查发现部分早期 method 卡仍只是指标名称和通用问句。例如：

- `method.memory.coalesced_access` 用 L1 命中率作为区分问题；命中率不能直接说明一次 warp 访问是否合并。
- `method.memory.register_pressure` 询问 occupancy 限制是否满足 workload 验收，却没有区分寄存器限制、真实 spill、ILP 与可用并行度。
- `method.compute.tensor_core` 只问某个 tensor pipe 指标是否达标，没有充分解释指令路径、问题规模与供数/同步之间的关系。

它们是建议材料，不是自动 gate；这里指出的是知识质量问题，不声称已经证明这些卡造成了某次实际失败。应改写已有内容，不能用新增卡掩盖旧内容。

现有 NCU 解析器只建模七类指标，按匹配行取均值，并明确记录聚合方式。这样的摘要不适合回答每个 launch、源码行或动态指令的问题。首轮不扩大解析器：需要时读已保存的原始报告或调用现有 Nsight 能力；不能从聚合值恢复它未保留的信息。

## 接入方式

### 1. 首轮只改三张已有卡

改写 coalesced_access、register_pressure、tensor_core，沿用现有字段和 ID。每张卡围绕一个真正能区分原因的问题组织材料，而不是罗列优化技巧：

- **合并访存**：结合访问宽度、活跃线程、地址布局和请求/sector 数据，区分不合并访问、重复访问、缓存效应与尾块。先查地址表达式和已有报告，再决定是否需要额外采样；低命中率不直接触发向量化。
- **寄存器压力**：结合编译器资源报告、live range、local traffic 和已有 timing，区分 occupancy 限制与 spill；同时考虑工作量不足、流水深度和 ILP。降低寄存器或缩小 tile 可能降低复用、增加指令或引入 spill，不作为默认答案。
- **Tensor Core 利用**：先确认精度要求、目标架构和实际生成路径，再判断是未使用适用指令、问题规模/尾块不足，还是供数或依赖限制。静态指令存在不等于运行，更不等于收益；只有结论确实依赖动态执行时才追加对应观测。

内容以官方文档、编译器输出定义和具体参考源码核验。论文与 Wiki 用于定位资料，不单独证明硬件契约。历史性能数字不加入当前收益预测。

不创建固定“诊断包”对象。必要的解释留在已有分析和 Experiment 前提中；无需每次填完整模板。

### 2. 外部材料作为可选阅读入口

在现有 `research_augmentation.md` 的来源选择处简要加入 KernelWiki：有架构/API/布局疑问时，定向读相关页面，追到 owning repository 的具体实现。优先使用当前已部署源码；已安装或已有 checkout 可直接搜索，无需安装另一套 skill。

`knowledge_query.py` 继续只查本地材料，不承担网络检索；不建聚合 API、自动爬虫或依赖更新服务。无网络时使用精简后的本地卡和部署源码，不把旧资料当最新，也不因为没有外部结果停止优化。

首次阅读以回答当前问题所需的少量页面为准；不是加载整份架构包，也不设置会截断关键同步契约的硬性 token 阈值。资料是否继续展开由未解决问题决定。

### 3. 验证作为配套工作，不另立 benchmark 项目

先用公开、可复核材料检查改写卡是否能回答上述区别。按现有项目演进模板，在结果产生前固定材料、比较版本与允许结论，不再发明模板。

首轮采用三组短的公开材料回放：寄存器/occupancy、访存请求/缓存、目标指令/实际执行。每组包含足够支持一个解释的材料和一个关键事实不同的反例；不要求历史命令逐条复现，不做字符串断言。改写前后使用同模型设置、相同证据与授权，材料中不放参考答案。保存分析结论、引用、所选下一步及成本；材料已公开，结果只能作为定向回归，不声称盲测泛化。

评估关注是否：区分原因；承认缺失证据；选到能区分原因的便宜观测；避免无必要的代码修改/采样；不把指令存在当收益。分别记录 token、额外工具调用和耗时，不压成黑盒总分。

少量回放不足以证明普遍提速。若结果不明确，报告未证明，不无限增加 case 寻找好看的结论。自动化测试只覆盖改动数据与现有接口的正常加载、适用性和输出，不把每句建议做成测试。

Atrex 保留为后续实际 GPU 评估的可选来源，不是首轮交付依赖。若使用，先固定公开 reference、shape、源码版本和本地环境，复用其现有 evaluator；只做一个与待验证改进相关的算子。只有本地重测基线才可比较，不能移植其 XPU-A/H20 权重或 roofline；算子结果不能支持完整服务加速声明。出现庞大适配成本时不为本轮研究重写 harness。

## 修改范围与分步交付

| 步骤 | 交付 | 不包含 |
|---|---|---|
| A：改写内容并核对来源 | `cards.json` 中三张卡、必要的 `sources.json` 精确来源；`ncu_metrics_guide.md` 用少量诊断说明替换浅层提示 | 卡片数量增长、Python 修改、新 playbook/协议、安装新 skill |
| B：接好资料入口 | `research_augmentation.md` 的来源选择与 `docs/knowledge-and-research.md` 对应说明 | 新检索服务、整库镜像、改写 `SKILL.md` 主流程 |
| C：有界验收 | 现有测试及三组定向回放；按现有演进模板记录结果与限制 | 全量 benchmark、长时间 GPU 搜索、宣称模型能力普遍提升 |

A、B 可形成一个小内容变更；C 是交付检查，不是先建实验平台。若现有字段不能表达这些内容，先缩小或重写内容，不顺手扩大 schema。若实现时发现真实工具丢失必需证据，单独描述该问题及最小影响面，不混入本轮。

完成标准：三张卡给出可执行的诊断思路而不是指标口号；来源可追溯、架构不误用；查询仍有界且无匹配不阻塞；反例不被强行判成同一原因；无需新增生产代码。没有观察到效率提升就不宣称提升。README 只在实际交付后同步用户可感知变化，不预告“新分析引擎”。

本轮完成三张卡、来源定位及资料入口的修改；未提交、推送、发布，也未运行 GPU 或改动已安装 skill。卡片数量不变，生产代码和测试未变。新旧卡六题均判断合理，不能宣称效率提升；不自动扩展下一轮知识或实验工作。
